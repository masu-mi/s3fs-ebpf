# ExtFUSE との比較・技術的優位性分析

本ドキュメントは、FUSE アクセラレーションの代表的な先行研究である **ExtFUSE** (SOSP '19) と、本プロジェクトで採用する **eBPF × KFunc × `bpf_arena` 活用型アーキテクチャ** (Linux 6.9+) の比較・技術的優位性を整理したものです。

## 1. アーキテクチャ比較表

| **比較軸**         | **先行研究: ExtFUSE (SOSP '19)**                                                        | **本プロジェクト (Linux 6.9+ 最新構成)**                                            |
| --------------- | ----------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| **カーネル要求**      | Linux 4.x ~ 5.x                                                                     | **Linux 6.9+**                                                           |
| **基本設計**        | FUSE ドライバのパッチ拡張 + BPF Map                                                           | **ネイティブ VFS モジュール + `bpf_arena` + KFunc**                                |
| **メモリ共有**       | `BPF_MAP_TYPE_HASH` / `ARRAY`<br><br>  <br>  <br><br>(`bpf_map_lookup_elem` 呼び出し必須) | **`bpf_arena` (4GB 疎な共有メモリ)**<br><br>  <br>  <br><br>生の C ポインタによる完全ゼロコピー |
| **Verifier 制約** | **厳格な制約あり**<br>(ループ制限・命令数制限・複雑性制限)                                                  | **KFunc により回避可能**<br>(C 言語ネイティブの無制限アルゴリズム実行)                             |
| **Miss 時のパス**   | `/dev/fuse` 経由の同期 IPC (コンテキストスイッチ発生)                                                | `BPF_MAP_TYPE_RINGBUF` 経由の非同期通知 (Go デーモン)                                |

## 2. 4つの核心的優位性

### ① メモリ共有モデル：Map Lookup から完全ゼロコピー (`bpf_arena`) へ

- **ExtFUSE:**
    メタデータやキャッシュの参照に標準の BPF Map を使用します。データアクセスのたびに `bpf_map_lookup_elem()` システムコール・ヘルパーを呼ぶ必要があり、巨大なデータペイロードを扱う場合は Map バリュー領域へのデータコピーがボトルネックとなります。
- **本構成:**
    Linux 6.9 で導入された `bpf_arena` を採用。ユーザー空間（Go デーモン）とカーネル空間（eBPF/KFunc）で **同一の 4GB 仮想アドレス空間（生の C 言語ポインタ）を共有** します。`lookup` ヘルパー呼び出しすら不要であり、ポインタのデリファレンス（`*ptr`）のみでデータを読み書きする真のゼロコピー（Zero-copy Shared Memory）を実現します。
### ② 演算能力と複雑性：Verifier 制約の完全突破 (KFunc)

- **ExtFUSE:**
    純粋な eBPF プログラムとして実装されているため、カーネルの **eBPF Verifier（検証器）による厳しい制限（ループ上限、命令数上限、スタック制限）** を直接受けます。そのため、簡単なパス名照合（`lookup`）や属性参照（`getattr`）程度しか処理できません。
- **本構成:**
    複雑な処理（Radix Tree 走査、Parquet/SSTable 解析、XGBoost 決定木評価等）を、Verifier 制限を受けない C 言語ネイティブの関数 **（KFunc: Kernel Functions）** へ委譲します。これにより、「eBPF の動的フック機能・安全性」と「カーネルモジュールの無制限な演算能力」を両立させています。
### ③ VFS アーキテクチャ：FUSE パッチ依存の脱却

- **ExtFUSE:**
    既存の FUSE フレームワーク（`/dev/fuse`）を前提とし、カーネル側の FUSE ドライバ内に eBPF フックを挟んで「キャッシュヒット時のみ FUSE デーモンへの転送をスキップする」アプローチです。キャッシュミス時は従来通りの重い FUSE コンテキストスイッチが発生します。
- **本構成:**
    `/dev/fuse` 自体を完全に排除し、**最小限の独自 VFS モジュール（または `BPF_MAP_TYPE_STRUCT_OPS`）** を構築してマウントします。Miss 時も `bpf_ringbuf` を介して Go デーモンへ軽量に非同期通知を行うため、FUSE のキュー管理や IPC オーバーヘッドを根本から消去しています。
### ④ アプリケーション・セマンティクス：単なる VFS キャッシュから Push-down へ

- **ExtFUSE:**
    目的は「POSIX ファイルシステムの I/O（`lookup`, `read`, `getattr`）のレイテンシ短縮」に特化しています。
- **本構成:**
    `bpf_arena` 上のデータ構造を KFunc が直接解釈することで、単なるファイルキャッシュにとどまらず、「条件に合致しない Row Group の読み込みキャンセル」や「Bloom Filter による存在しない Key への I/O スキップ」といった **DB レイヤーの述語プッシュダウン（Predicate Push-down）** をカーネル空間内で透過的に実行できます。

## 3. 発表・ドキュメント用サマリー（ストーリーテリング）

> **「FUSE を eBPF で高速化するアプローチとして、2019 年の SOSP で発表された ExtFUSE という優れた先行研究が存在しました。しかし当時、彼らは BPF Map のルックアップコストと Verifier の厳格な命令数制限に悩まされていました。**
> **本プロジェクトは、Linux 6.9+ の最新機能である `bpf_arena` と KFunc を組み合わせることで、ExtFUSE が到達できなかった『生の C ポインタによる完全ゼロコピー』と『Verifier 制限を回避した高度な Push-down ロジックの実装』を同時に達成した、次世代の Fast-Path フレームワークです。」**

# RFUSE (FAST '24) との比較・技術的優位性分析

本ドキュメントは、FUSE アクセラレーションの最新研究である **RFUSE** (USENIX FAST '24) と、本プロジェクトの **eBPF × KFunc × `bpf_arena` 活用型アーキテクチャ** (Linux 6.9+) の比較・技術的優位性を整理したものです。

## 1. アーキテクチャの根本的な違い（コンセプト比較）

- **RFUSE (通信パイプの極速化):**
    従来の `/dev/fuse`（キャラクタデバイス）による遅い IPC を捨て、`io_uring` に着想を得た「Shared Memory 上の Ring Buffer」を用いてカーネルとユーザー空間デーモン間の通信を極限まで高速化しました。しかし、**「すべての要求（Read/Write/Lookup等）を一度ユーザー空間のデーモンに送って処理させる」** という FUSE 本来の構造は維持しています。
- **本フレームワーク (通信の完全排除 / アーリーリターン):**
    ユーザーデーモンへの通信を速くするのではなく、**「カーネル空間（KFunc）内で直接 `bpf_arena` のデータを評価し、ユーザー空間へ問い合わせることなくその場で即答（または破棄）する」** アプローチをとります。キャッシュヒット時や Push-down 判定時には **IPC（プロセス間通信）自体が 0 回（発生しない）** となります。

## 2. アーキテクチャ比較表

|                      |                                               |                                                           |
| -------------------- | --------------------------------------------- | --------------------------------------------------------- |
| **比較軸**              | **最新研究: RFUSE (FAST '24)**                    | **本プロジェクト (Linux 6.9+ 最新構成)**                             |
| **中核となる技術**          | Shared Memory Ring Buffer (カスタム IPC)          | **`bpf_arena` + KFunc + eBPF/VFS フック**                    |
| **ロジックの実行場所**        | ユーザー空間（FUSE デーモン）                             | **カーネル空間内（KFunc による事前評価）**                                |
| **Fast-Path 時の IPC** | **発生する** (高速な Ring Buffer 経由)                 | **ゼロ** (カーネル内で即答・完結)                                      |
| **コンテキストスイッチ**       | 削減されているが、ユーザーデーモンの Wakeup は伴う                 | **完全に発生しない (0 回)**                                        |
| **導入のハードル**          | カスタム FUSE カーネルモジュールとカスタム `libfuse` のビルド・置換が必要 | **Mainline Linux 6.9+ 標準機能**<br>(eBPF とカーネルモジュールの追加ロードのみ) |

## 3. 4つの核心的優位性

### ① 「高速な IPC」vs「ゼロ IPC (Early Cutoff)」

RFUSE は Ring Buffer を使ってカーネル ↔ ユーザー空間のデータ転送（コピー）を削減・高速化しました。しかし、結局はユーザーデーモン側でメタデータを引き、処理を行い、カーネルに結果を返す必要があります。

対して本構成は、KFunc が `bpf_arena`（Shared Memory）を直接走査するため、**ユーザー空間のプロセスを一切 Wakeup させることなく、カーネルの VFS フック層（`fentry` や `.read_iter`）の中で処理が完結**（Early Cutoff / アーリーリターン）します。
### ② DB ミドルウェアとしてのセマンティクス理解（Push-down）

RFUSE はあくまで「高速なファイルシステムインターフェース」であり、流れるデータの意味（Parquet、RocksDB SSTable、XGBoost の木構造など）を理解しません。

本構成は KFunc をプラグインとして注入できるため、**「検索条件（Predicate）に合致しないデータブロックへのアクセスに対して、I/O リクエスト自体をカーネル内で破棄する（Push-down）」** といった、単純な VFS の枠を超えた Smart Storage ミドルウェアとして機能します。
### ③ アップストリーム（Mainline）技術への準拠と導入容易性

RFUSE はカーネル内の FUSE ドライバ（`fuse.ko`）そのものに大規模なパッチを当て、ユーザー空間の `libfuse` も独自フォーク版へ差し替える必要があります。これは本番環境への導入障壁が非常に高いアプローチです。

本構成は、Linus Torvalds がマージした **Linux 6.9+ の標準メインライン機能（eBPF, `bpf_arena`, KFunc, `struct_ops`）だけを使用** しています。カーネル本体にパッチを当てることなく、動的なモジュールロードだけで安全に適用できる点で、実用性に圧倒的な分があります。
### ④ メモリ一貫性モデルと安全性

RFUSE は独自の Shared Memory 上の Ring Buffer を C 言語で手組みして管理しています。

対して本構成は、eBPF コミュニティが心血を注いで設計した `bpf_arena` インフラに乗っかっています。Verifier による安全性チェック（一部 KFunc で回避するものの）、`BPF_MAP_TYPE_RINGBUF` によるカーネル標準のイベント通知機構など、**最新の eBPF エコシステムの堅牢なインフラストラクチャをそのまま再利用・享受できる** 強みがあります。

> **「FUSE のパフォーマンスを改善する最新のアプローチとして、FAST '24 で発表された『RFUSE』があります。彼らは Ring Buffer を用いてカーネル・ユーザー間の通信（IPC）を極限まで高速化し、FUSE の限界を押し広げました。」**
> 
> **「しかし、我々のアプローチは『通信を速くする』ことではありません。Linux 6.9 の `bpf_arena` と KFunc を組み合わせることで、『そもそもユーザー空間への通信を発生させず、カーネル内で処理を完結させる（ゼロ IPC）』パラダイムへと進化させました。RFUSE が『超高速な土管』を作ったとすれば、我々は DB の述語評価すらカーネル内で短絡させる『スマートな門番（Smart Accelerator）』を作ったと言えます。」**
