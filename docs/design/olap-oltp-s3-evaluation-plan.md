# S3 利用系の OLAP / OLTP エンジンに対する評価計画 (DuckDB など)

2026-10-27。計画のみ (未実施)。`ann-workload-measurement-plan.md` の次の評価。

DuckDB のように S3 を直接読むエンジンは、FS を挟んでいないものが多い。そこでこの文書は、まず「FS を挟む価値が本当にあるか」を安く確かめる手順 (ゲート) を置き、通ったときだけ本計測に進む。価値がないと分かった場合も、それは結果として残す。

本体 (kmod / daemon) のバグ訂正と再計測が進行中なので、kmod を使う段階 (E3) はその完了後に行う。E0〜E2 は本体に依存しない。

## 1. 先に言える見立て

- エンジンが**自前の永続・共有データキャッシュを持つなら、FS 層の出番は小さい**。ClickHouse は S3 上のバイト範囲 (数 MB の単位) を local の filesystem cache に置く read-through cache を持つ ([ClickHouse docs](https://clickhouse.com/docs/cloud/clickhouse-private/explanation/clickhouse-filesystem-cache))。
- DuckDB の httpfs は HTTP の range request で必要な範囲だけを読む ([DuckDB docs](https://duckdb.org/docs/current/guides/network_cloud_storage/s3_import))。データブロックの永続キャッシュは、コミュニティ拡張 [cache_httpfs](https://duckdb.org/community_extensions/extensions/cache_httpfs.html) が補う形で、メタデータ・グロブ・ファイルハンドル・データブロックのキャッシュ (メモリ/ディスク、LRU など) を持つと説明されている。公式の既定構成には、データの永続キャッシュはないと理解している (要確認: 手元のバージョンで確認する)。
- したがって、FS 層が有効と言える余地は「エンジン側のキャッシュが**ない、または届かない**ところ」に限られる。§3 で仮説にし、§4 のゲートで潰せるものから潰す。
- OLTP は期待が低い。S3 を正本にする OLTP は、ページサーバ型や LSM 型 (自前のキャッシュ層を持つ) が多く、更新と fsync の意味 (この PoC の E-01) が FS 層の弱点でもある。読み取り側の一部 (§3 H6) だけを候補に残す。

## 2. 対象の整理

| 区分 | 例 | S3 への繋ぎ方 | 自前のキャッシュ | 備考 |
|---|---|---|---|---|
| OLAP (組み込み) | DuckDB | httpfs (HTTP range) | 公式は主にメタデータ。データは cache_httpfs 等 | 本命。Parquet を直接読む |
| OLAP (サーバ) | ClickHouse | S3 disk | filesystem cache あり | 比較対象。FS 層は重複しやすい |
| OLAP (分散) | Spark / Trino 系 | S3A / 独自コネクタ | 構成による (要確認) | 今回は対象外にして、必要なら後で |
| ライブラリ | pyarrow / polars | 各自の S3 実装、または POSIX | ほぼなし (要確認) | FS 経由なら無改造で効く |
| OLTP 寄り | SQLite / RocksDB 系 | ローカルファイル | OS の page cache | S3 は上位の仕組み (Litestream、cloud 版 など。要確認) |
| OLTP (S3 ネイティブ) | ページサーバ型 / LSM 型 | 独自 | 独自 | FS を挟む余地は小さい。対象外 |

既存の比較 (FUSE / Mountpoint との位置付け) は `docs/user/related-works.md` にある。ここでは重複して書かない。

## 3. FS を挟む価値の仮説

| # | 仮説 | 成り立つ条件 | 反証されるとき |
|---|---|---|---|
| H1 | エンジンにデータの永続キャッシュがなく、再起動・コールドスタートで毎回 S3 から読み直す | 素の httpfs など | cache_httpfs が同等の効果を出す |
| H2 | 同じホストの複数プロセス (別の DuckDB プロセス、ワーカー) がキャッシュを共有できる | プロセスごとに別のキャッシュ | エンジンのキャッシュが共有できる / 1 プロセスで足りる |
| H3 | 無改造・多言語のクライアント (pyarrow、polars、closed-source) が同じキャッシュを使える | POSIX で Parquet を読める | 利用側がもともと自前のキャッシュを持つ |
| H4 | キャッシュ policy を、エンジンを変えずに運用側で差し替えられる (走査に強い policy、先読み) | エンジンの policy が固定か、チューニング不可 | エンジン側 policy でも同じ効果 |
| H5 | ヒット時にカーネル内 (page cache) で返り、ユーザー空間のキャッシュより CPU と遅延が小さい | 小さな読みが多い | エンジンの読み方が大きく連続で、差が出ない |
| H6 | (OLTP 寄り) 不変の SST / base file を読む側で、更新は別の経路に任せる | 読み取りの比率が高い | 書き込みの意味 (fsync、rename) で破綻する |

**Parquet / Iceberg / Delta のデータファイルは不変**である点は、この PoC に有利に働く。キャッシュの無効化が実質不要になり、`docs/design/pcache-mode.md` の複雑な部分 (書き込みと整合) を避けられる。一方、ファイルが差し替わる運用 (同名上書き) は対象外と明記する。

## 4. ゲート (安く潰す順)

各ゲートで「FS 層が要らない」と分かったら、そこで止めて結論を書く。

| ゲート | 確かめること | 方法 | 止める条件 |
|---|---|---|---|
| G0 | 現行のエンジンが何をキャッシュするか | DuckDB / ClickHouse / pyarrow の設定とドキュメントを読み、小さな実験で確認する。MinIO の request log で GET 数を見る | 想定が間違っていたら、§2 の表を直して仮説を見直す |
| G1 | 読みの形が、この PoC の得意な形か | ClickBench / TPC-H の Parquet を MinIO に置き、DuckDB の読み (範囲、サイズ、順序、再利用) を採取する (§5 E1) | ほぼ全部が 1 回きりの大きな連続読みで、再利用が小さい (キャッシュの余地が小さい) |
| G2 | 既存の代替より良いか | 素の httpfs / cache_httpfs / mountpoint-s3 / 本 FS を、同じ条件で比べる (§5 E3) | cache_httpfs で H1〜H5 のほぼ全部が説明される |

G2 に通らなくても、H2 (複数プロセスの共有) と H3 (無改造クライアント) だけが残る、といった**部分的な結論**を書く。

## 5. 評価計画

### E0 現状調査 (本体に依存しない)

- DuckDB (httpfs、cache_httpfs)、ClickHouse、pyarrow / polars の S3 読みの実装と既定のキャッシュを、ドキュメントと小さな実験で確認する。
- 成果: §2 の表の「要確認」をなくす。

### E1 アクセスパターンの採取

- データ: ClickBench (単一テーブル)、TPC-H (SF10 / SF100)、TPC-DS の Parquet。Parquet の row group の大きさ、ファイル数、パーティション構成も変数にする。
- 採取: MinIO の access log、または DuckDB の HTTP ログから、`(object, off, len, qid)` を取り出して trace にする。`ann-workload-measurement-plan.md` P0 の拡張 trace 形式をそのまま使う (ここで道具を共有する)。
- 見るもの: クエリ内の再利用 (同じ row group の再読み)、クエリ間の再利用 (同じ列・同じファイル)、フッタ (メタデータ) の読み、読みのサイズ分布。

### E2 policy の simulator 比較

- E1 の trace を `trace-replay` で、LRU / SIEVE / S3-FIFO / W-TinyLFU と OPT 近似に流す。容量はデータ全体の 1% / 5% / 10% / 25%。
- 見る問い:
  - フッタとメタデータのホット保持 (一度きりの大きな列走査に押し出されないか)。
  - ワークロード別の policy の順位 (ClickBench 風の短い分析 / TPC-H 風の大きな走査)。
  - 先読みの効果 (row group の次、同じ列の次のファイル)。
- 成果: G1 の判定資料。ここまでで「キャッシュの余地がどれだけあるか」の上限が出る。

### E3 end-to-end の比較 (本体の再計測後)

比較する構成:

| 記号 | 構成 |
|---|---|
| A | DuckDB + 素の httpfs → MinIO |
| B | DuckDB + cache_httpfs → MinIO |
| C | DuckDB + mountpoint-s3 (FUSE) → MinIO |
| D | DuckDB + s3fs-ebpf (pcache) → MinIO |
| E | ClickHouse + 自前 filesystem cache → MinIO (参照のみ) |

シナリオ:

1. コールド 1 回 (キャッシュ空)。
2. ウォーム (同じクエリの繰り返し)。
3. プロセス再起動後 (H1)。
4. 複数プロセスが同時に別クエリ (H2)。
5. pyarrow / polars から同じファイルを読む (H3)。
6. 走査クエリのあとにホットなクエリを流す (H4 / scan 耐性)。

指標: クエリのレイテンシ (p50 / p99)、S3 GET 数と取得バイト数、CPU 時間、メモリ使用量、ヒット率。

**重要な注意**: DuckDB は、ローカルのパスと httpfs とで読み方が違う可能性がある (読みの束ね方や先読みなど。要確認)。FS 経由にすると、エンジンの最適化が変わって比較が歪む。構成 A〜D の GET の数・サイズ・順序を E1 の採取で比べ、読み方が違う場合は「FS 層の効果」と「読み方の変化の効果」を分けて報告する。

### E4 OLTP 寄りの候補 (任意、優先度は低い)

- H6 の確認だけ行う。例: SQLite の読み取り専用の DB、または RocksDB の SST を S3 に置いて読む。更新は別経路にする。
- 書き込み側 (fsync、rename、途中の書き換え) は、この PoC の E-01 / AC-51 の既存の限界のとおり、対象外と明記する。
- G0〜G2 の結果が OLAP で十分に出てから判断する。出なければやらない。

## 6. 提案できる道筋 (結果ごと)

| 結果 | 言えること |
|---|---|
| G2 で FS 層が cache_httpfs と同等以上で、H1・H2・H3 が示せた | 「エンジンを変えずに使える共有のホストキャッシュ」として提案できる。特に複数プロセス・多言語クライアント |
| FS 層は同等だが、H4 (policy の差し替え) だけが示せた | 「policy を運用側で差し替える実験の場」として提案できる。エンジン非依存の policy 研究の基盤 |
| 既存の代替で十分 (G2 で止まる) | 「DuckDB のような既存エンジンには不要」を結論にする。ベクトル検索など、エンジンが自前のキャッシュを持たない領域 (`ann-workload-measurement-plan.md`) に絞る |
| G1 で再利用が小さい | 「分析ワークロードは多くが 1 回きりの走査で、キャッシュの上限が小さい」を結論にする。一般的な知見として価値がある |

どの結果になっても記録に残す。「FS を挟む価値がない」と分かること自体が、一般的に価値のある知見になる。

## 7. 妥当性への脅威

| 脅威 | 対処 |
|---|---|
| MinIO と本物の S3 とでレイテンシが違う | 絶対値は報告せず、構成間の比で報告する。可能なら本物の S3 で数点だけ確認する |
| DuckDB / cache_httpfs のバージョン差 | バージョンを固定して記録する。cache_httpfs は community extension なので、リリース状況を E0 で確認する |
| FS 経由で読み方が変わる (E3 の注意) | GET の数・サイズ・順序を構成間で比べる |
| TPC-H / ClickBench が実運用と違う | 複数のデータセットと、Parquet の構成違いで測る。実運用の trace があれば差し替えられる形にする |
| 本体のバグ訂正前の数値の混入 | E3 は本体の再計測完了後にのみ実施する。それまでは E0〜E2 のみ |
| 比較対象の設定が不利 | 各構成の設定を、公式ドキュメントの推奨に沿って揃え、設定を成果物に残す |

## 8. 成果物と進め方

- `docs/journal/olap-s3-results.md` (結果の表と、§6 のどの結論になったか)。
- E1 の採取スクリプト (MinIO log → 拡張 trace)。ANN 計画の P0 と共有する。
- 進め方: E0 → E1 → E2 を先に行い、G1 の判定を出す。E3 は本体の再計測が済んでから。

| 段階 | 規模の目安 | 本体への依存 |
|---|---|---|
| E0 | 小 | なし |
| E1 | 中 (環境: MinIO、データ生成) | なし |
| E2 | 小 (ANN 計画の P0 が済めば) | なし |
| E3 | 中〜大 | あり (再計測後) |
| E4 | 小〜中 (任意) | あり |

## 9. 決めておきたいこと

- E3 の比較対象に mountpoint-s3 を含めるか。FUSE との比較は価値があるが、設定と環境の手間が増える。
- 本物の S3 での確認を、どの段階で何点行うか (費用と環境の都合)。
- Spark / Trino 系を対象に含めるか (今回は外す案)。
- OLTP (E4) を計画に残すか、最初から外すか。
