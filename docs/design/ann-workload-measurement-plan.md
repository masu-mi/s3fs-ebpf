# ANN 検索 (IVF / HNSW) のアクセスパターンでキャッシュ policy を比べる計測計画

2026-10-27。計画のみ (未実施・未実装)。turbopuffer のような「S3 を正本にして SSD/メモリでキャッシュするベクトル検索 DB」に、この PoC の policy 層 (LRU / SIEVE / S3-FIFO / W-TinyLFU、admit / softcap、prefetch) の知見が使えるかを、実測で確かめる。

turbopuffer 自体の内部は非公開なので、ここでは「IVF 系 (大きな連続読み) と HNSW 系 (小さなランダム読み) の 2 つの極」を再現し、特定の製品に依らない一般的な結論を得ることを目標にする。

## 1. 問い

| # | 問い | 答えの使い道 |
|---|---|---|
| Q1 | IVF のクラスタ読みと HNSW のノード読みで、policy の順位は入れ替わるか | policy をワークロード別に切り替える根拠 |
| Q2 | 同じキャッシュ容量でのヒット率 (リクエスト数と**バイト数**) は、どの policy で最大になるか | 容量設計 |
| Q3 | 1 クエリあたりの S3 GET 数と取得バイト数は、policy と容量でどう変わるか | コストとレイテンシの見積り |
| Q4 | 先読み (`prefetch_next`、重心表の prewarm) は、IVF で何 % の miss を消せるか。HNSW では効くか | 先読み設計 |
| Q5 | 一度きりの大きな走査 (IVF のコールドクラスタ) が、ホットな小さいデータ (重心表、HNSW 上位層) を押し出すか。admit 制御 (TinyLFU の門、softcap) で防げるか | scan resistance の定量化 |
| Q6 | chunk の大きさ (256 KiB 〜 4 MiB) は、どちらのワークロードでも妥当か | chunk サイズの選び方 |

Q5 と Q6 は、ANN に限らず「大きな走査と小さなホットデータが混在する読み取り中心のワークロード」に当てはまる、一般的な知見になる。

## 2. 現状の道具と足りないもの

`s3fs-ebpf dev trace-replay` (`docs/design/trace-harness.md`) は、ms 単位で policy を比べられる。ただし今のままでは ANN に使えない。

| 項目 | 現状 | ANN に必要なもの |
|---|---|---|
| trace のキー | `ino` (ファイル全体) | `(ino, chunk)` または `(ino, offset, len)` |
| 容量の単位 | エントリ数 (`softcap`) | バイト (chunk ごとに重みが違う) |
| 評価指標 | ヒット率 (リクエスト) | バイトヒット率、GET 数、取得バイト数 |
| policy | lru / sieve / s3fifo / wtinylfu / opt / noevict | 同じ (入口の型だけ変える) |
| 先読み | なし | 次の chunk / 指定集合の先読みを模擬 |

実 kmod の pcache は 4 MiB の chunk 単位で動く (`docs/design/pcache-mode.md` §3)。そこで trace の粒度も chunk に合わせるのが素直。

## 3. ワークロードの定義

### 3.1 IVF 型

インデックスを 1 ファイル (またはクラスタごとのオブジェクト) に並べ、次の順で読む。

1. 重心表を読む (小さい、毎クエリ)。
2. 近い順に `nprobe` 個のクラスタを選び、各クラスタの全体を連続して読む。
3. 結果の再ランク用に、元ベクトルを少数読む (ランダム、小さい)。

主なパラメータ:

| パラメータ | 値の候補 |
|---|---|
| ベクトル数 N | 1M / 10M / 100M |
| 次元 d | 128 / 768 |
| クラスタ数 | √N 〜 4√N |
| `nprobe` | 1 / 8 / 32 |
| クラスタの人気分布 | 一様 / Zipf(0.7) / Zipf(1.1) |
| クラスタの大きさ | 一様 / 偏りあり (ログ正規) |

クエリの分布が偏る (人気のクラスタがある) かどうかが、キャッシュの効き方を決める。この偏りは入力の仮定なので、必ず複数の値で測る。

### 3.2 HNSW 型

グラフを層ごとのノード配列として並べ、次の順で読む。

1. 最上層の入口から、近い隣接へ貪欲に辿る。
2. 層を降り、最下層で `efSearch` 個の候補を広げる。
3. 各ノードで、近傍リストとベクトル本体を読む。

主なパラメータ:

| パラメータ | 値の候補 |
|---|---|
| N | 1M / 10M |
| `M` (近傍数) | 16 / 32 |
| `efSearch` | 50 / 200 |
| ノードの並び | 挿入順 / グラフ局所性で並べ替え (BFS 順) |
| クエリの分布 | 一様 / 既存ベクトル近傍に偏る |

ノードの並び (レイアウト) が局所性を大きく変えるので、これも変数にする。

### 3.3 混在型 (Q5 用)

IVF 型 + 重心表のホット読み + 「一度きりの大きな走査」(別 namespace の全件スキャン) を同じキャッシュに流す。

### 3.4 参照用

既存の Zipf (ファイル単位) を、そのまま基準として残す。新旧の結果をつなぐため。

## 4. 段階

小さく始め、各段階で結論を出せる形にする。

### P0 trace の拡張 (ms 単位の simulator)

- trace に `off` と `len` を足す (後方互換: 無ければ従来どおり)。
  `{"ts":0,"ino":100,"off":8388608,"len":4194304,"op":"read"}`
- simulator のキーを `(ino, off/chunk)` にし、容量をバイトで数える。chunk 以外のサイズのエントリは `len` を重みにする。
- 出力に、バイトヒット率、miss 数、miss バイト数 (= S3 から取る量) を足す。
- 受け入れ: 既存の trace (キーが `ino` のみ) の結果が変わらない回帰テスト。

### P1 合成 trace の生成器

- IVF 型、HNSW 型、混在型を、パラメータを指定して JSON Lines に出す生成器を `daemon/cmd` の `dev` サブコマンドに足す。
- seed を固定する。Go と Python の乱数は別物なので (`trace-harness.md` の注意)、生成は Go 側に統一する。
- 受け入れ: 同じ seed で同じ trace が出ること。ワークロードごとの「1 クエリあたりの読み」(件数、バイト数) の分布が、手計算と一致すること。

### P2 simulator での policy 比較 (Q1, Q2, Q4, Q5)

- 計測行列: ワークロード (3.1〜3.3) × 容量 (データ全体の 1% / 5% / 10% / 25%) × policy。
- 容量はデータ全体に対する比で指定する。絶対値だと結果が一般化できない。
- 先読み (Q4) は simulator に「IVF のクラスタ内の次の chunk を先に入れる」を足して、有無を比べる。
- 各点 5 seed で平均と範囲を出す。順位の差が seed 間のばらつきより大きいときだけ「差がある」と書く。
- OPT (Belady) と noevict を上下限として必ず並べる。

### P3 実データでの妥当性確認

合成 trace が現実と離れていないかを確かめる。

- 公開データセット (SIFT1M、GIST1M、Deep など) で、faiss (IVF) と hnswlib (HNSW) のインデックスを作る。
- インデックスを `mmap` で開いたプロセスのページ読みを記録して trace にする。記録は `perf trace` / `bpftrace` (`filemap` 系 tracepoint) / `strace -e pread64` のいずれか。
- 合成 trace と実 trace で policy の順位が一致するかを見る。一致しない場合は、生成器のパラメータ (人気分布、局所性) を直す。
- 受け入れ: 順位の一致 (または不一致の理由の説明) が、表になっていること。

### P4 実 kmod での確認 (少数点のみ)

- simulator の差は、実機と一致するとは限らない (`trace-harness.md` の注意: BPF 版は 25 アクセスごとの評価など、ずれがある)。
- P2 で差が大きかった 2〜3 点に絞り、`scripts/bench-hitrate.sh` 相当で MinIO を相手に実測する。
- 追加で測るもの: miss 時の upcall のレイテンシ、1 クエリあたりの GET 数、chunk を変えたときの変化 (Q6、`S3FS_CHUNK_SIZE` はビルド時定数のため、2〜3 値でビルドし直す)。
- 注意: 実機の結果は S3 ではなく MinIO のレイテンシで測るので、絶対値ではなく policy 間の比を報告する。

## 5. 指標

| 指標 | 定義 | 使う問い |
|---|---|---|
| リクエストヒット率 | hit 数 / read 数 | Q1 |
| バイトヒット率 | hit バイト / 読んだバイト | Q2 |
| GET 数 / クエリ | miss の回数 / クエリ数 | Q3 |
| 取得バイト / クエリ | miss バイトの合計 / クエリ数 | Q3 |
| ホット保持率 | 重心表・上位層の chunk が、走査のあとも残っている割合 | Q5 |
| 先読み精度 | 先読みした chunk のうち、後で使われた割合 | Q4 |
| 先読みによる miss 削減 | 先読みなし比の miss 数の減少 | Q4 |

クエリ単位の指標を出すため、trace にクエリの区切り (`qid`) を足す。レイテンシは P4 以外では直接測れないので、GET 数 (直列に待つ回数) を代理として使う。HNSW は依存連鎖の読みなので、**直列の GET 数** (連鎖の深さ) も別に数える。

## 6. 妥当性への脅威

| 脅威 | 対処 |
|---|---|
| 人気分布は入力の仮定で、結果が仮定に引きずられる | 一様・Zipf の複数値で測り、結論を「どの範囲で成り立つか」で書く |
| 合成 trace が現実と違う | P3 で実 trace と順位を照合する |
| simulator と実 BPF 版のずれ | P4 で少数点を実機確認する。差が出たら simulator 側の差として記録する |
| 実装の中身を知らない製品を名指ししてしまう | 結論は「IVF 型 / HNSW 型」に対して書き、特定製品の性能は主張しない |
| ストレージ側 (S3 の GET レイテンシ、並列度) を無視している | GET 数と直列の深さを出し、レイテンシへの換算は読者に委ねる |
| 1 つの実装 (faiss / hnswlib) の癖 | P3 で 2 つ以上の実装またはレイアウトを使う |

## 8. 進め方と見積り

| 段階 | 内容 | 規模の目安 |
|---|---|---|
| P0 | trace 拡張 | 小 (simulator の入口の型の変更が中心) |
| P1 | 生成器 | 小〜中 |
| P2 | 比較の実行と整理 | 小 (P0, P1 が済めば ms 単位で回る) |
| P3 | 実データ | 中 (インデックス作成と記録の環境が要る) |
| P4 | 実機確認 | 中 (kmod を使う環境が要る。この計画の外でも実施可) |

P0〜P2 だけでも Q1, Q2, Q4, Q5 の一次的な答えが出る。まずそこまでを実施し、結果を見て P3 以降に進むかを決める。

## 9. 決めておきたいこと

- chunk の大きさの既定: 実 kmod に合わせて 4 MiB で始めるか、ANN の読みに合わせて小さくするか (Q6 で比べる前提で、4 MiB を基準にする案)。
- OPT をバイト容量・可変サイズで厳密に出すのは難しい (可変サイズの最適は NP 困難)。サイズ一定の近似にするか、上界として「不等式で近似した値」と明記するか。
- P3 のデータセットの選定 (ライセンスと、サイズの現実性)。
